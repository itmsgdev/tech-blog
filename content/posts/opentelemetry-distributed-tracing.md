# OpenTelemetry로 분산 시스템 가시성 확보하기

마이크로서비스 아키텍처를 도입하고 나서 가장 머리 아픈 문제가 하나 생겼습니다. 서비스가 하나둘 늘어나면서 장애가 터졌을 때 "대체 어디가 문제야?"라는 질문에 답하기가 너무 어려워진 것입니다. 예전엔 로그 몇 개만 봐도 금방 찾을 수 있었는데, 이제는 여러 서비스를 오가며 수사를 해야 하는 상황이 되었습니다. 그래서 **OpenTelemetry 기반의 분산 트레이싱 시스템**을 도입하게 되었고, 그 과정에서 얻은 경험을 정리해보려 합니다.

## 🔍 왜 분산 트레이싱이 필요할까요?

예전 모놀리식 시절엔 단순했습니다. 에러가 나면 해당 서버 로그만 뒤지면 답이 나왔죠. 그런데 마이크로서비스로 쪼개고 나니:

- 사용자 하나가 버튼 누르면 뒤에서 5~6개 서비스가 우다다 움직여요
- 각 서비스마다 로그가 따로 쌓여서 추적이 힘들어졌습니다  
- "A 서비스에서 B 서비스 호출했는데 왜 안 되지?" 같은 상황 파악이 어려워졌어요
- 느린 구간이 어딘지 찾으려면 서비스마다 하나씩 뒤져야 했습니다

결국 **분산 트레이싱** 없이는 장애 대응이 너무 고통스러웠습니다.

## 🌐 OpenTelemetry를 선택한 이유

처음엔 Jaeger, Zipkin 같은 툴들도 고려해봤는데, [OpenTelemetry](https://opentelemetry.io/)로 결정한 이유는:

- **벤더 중립적**: 나중에 다른 모니터링 도구로 갈아타기 쉬워요
- **언어 지원이 좋음**: 저희가 쓰는 Java, Python, Go 다 지원합니다
- **자동 계측**: 기존 코드 건드리지 않고도 많은 걸 자동으로 추적해줘요
- **업계 표준**: 이제 대부분 여기로 몰리는 추세입니다

무엇보다 한번 설정해두면 데이터 포맷이 표준화되어 있어서 나중에 분석 도구를 바꿔도 데이터는 그대로 쓸 수 있다는 점이 매력적이었습니다.

## 📊 실제로 어떤 데이터가 모일까요?

OpenTelemetry 붙이고 나니 이런 데이터들이 쌓이기 시작했습니다:

### 1. 트레이스 (Traces)
사용자가 뭔가 하면 그게 어디를 거쳐서 어떻게 처리되는지 전체 여행 경로가 보입니다.

```
사용자 요청 → API Gateway → 사용자 서비스 → 주문 서비스 → 결제 서비스 → 외부 API
     ↓              ↓            ↓           ↓          ↓
  100ms          50ms         200ms       150ms      300ms
```

### 2. 스팬 (Spans)  
각 서비스에서 "뭘 얼마나 오래 했는지" 기록한 단위입니다.

- 어떤 서비스에서 뭘 했는지
- 언제 시작해서 언제 끝났는지
- HTTP 응답코드가 뭐였는지
- 데이터베이스에 어떤 쿼리 날렸는지
- 에러가 났다면 어떤 에러인지

### 3. 메트릭 (Metrics)
숫자로 보는 시스템 건강 상태입니다.

- 요청이 분당 몇 개씩 들어오는지
- 평균 응답시간이 얼마인지  
- 에러가 몇 퍼센트나 발생하는지
- 각 서비스가 얼마나 바쁜지

## 🎯 대시보드 만들어서 써보니

데이터만 쌓아두면 뭐하겠어요? 봐야 의미가 있죠. 그래서 몇 가지 대시보드를 만들어 봤습니다.

### 서비스 맵 (Service Map)
누가 누구를 호출하는지 한 눈에 보입니다. 마치 지하철 노선도 같은 느낌이에요.

```
[Frontend] → [API Gateway] → [User Service]
                    ↓
              [Order Service] → [Payment Service]
                    ↓              ↓
              [Inventory Service] [External API]
```

- 초록불: 정상, 노간불: 좀 느림, 빨간불: 뭔가 이상함
- 선이 굵을수록 호출이 많은 것
- 클릭하면 상세 정보 확인 가능

### 트레이스 상세 뷰
특정 요청이 정확히 어디서 시간을 잡아먹었는지 보여줍니다. 이게 진짜 꿀이에요.

{{< mermaid >}}
gantt
    title 트레이스 상세 뷰 (Request ID: abc123-def456)
    dateFormat X
    axisFormat %Lms
    
    section API Gateway
    Gateway Processing :done, gateway, 0, 50
    
    section User Service  
    User Processing :done, user, 50, 150
    Database Query :done, userdb, 70, 150
    Cache Lookup :done, cache, 130, 150
    
    section Order Service
    Order Processing :done, order, 150, 350
    Validate Order :done, validate, 150, 200
    Save to DB :done, orderdb, 200, 350
    
    section Payment Service
    Payment Processing :crit, payment, 350, 850
    External API Call :crit, extapi, 350, 800
    Update Status :done, update, 800, 850
{{< /mermaid >}}

**총 소요시간: 850ms**
- API Gateway: 50ms ✅
- User Service: 100ms (DB 쿼리 80ms, 캐시 20ms) ✅
- Order Service: 200ms (검증 50ms, DB 저장 150ms) ✅  
- Payment Service: 500ms ⚠️ (외부 API 450ms ⚠️, 상태 업데이트 50ms)

이거 보면 "아, 결제 서비스에서 외부 API 호출 때문에 느려지는구나"하고 바로 알 수 있어요.

### 성능 메트릭 차트
시간에 따라 시스템이 어떻게 변하는지 그래프로 봅니다.

- **응답시간 분포**: 보통은 100ms인데 가끔 2초 찍는 애들 있어요
- **요청량 추이**: 점심시간에 몰리고 새벽엔 조용해요  
- **에러율 변화**: 어제 배포 후에 에러가 좀 늘었네요?
- **의존성 성능**: 외부 API가 오늘따라 느립니다

### 알림 설정
이상한 일이 생기면 슬랙으로 톡 날아옵니다.

- 응답시간 1초 넘으면 알림
- 에러율 5% 넘으면 알림  
- 특정 서비스 죽으면 바로 알림
- 외부 API 계속 실패하면 알림

새벽에 깨기 싫어서 알림 임계값 조정하는 게 은근 중요해요.

## 🔧 도입하면서 고생한 부분들

### 1. 샘플링 전략
처음엔 모든 요청을 다 추적했다가 서버가 죽을 뻔했어요.

```
- 트래픽 많은 API: 1% 샘플링
- 보통 API: 10% 샘플링  
- 트래픽 적은 API: 100% 샘플링
- 에러 발생하면: 무조건 추적
```

적당히 타협점을 찾는 게 중요합니다.

### 2. 데이터 저장소 고민
트레이스 데이터가 엄청 쌓입니다. 어디에 저장할지 고민이 많았어요.

- **시계열 DB**: InfluxDB, TimescaleDB - 시간 기반 쿼리에 빨라요
- **NoSQL**: Elasticsearch, Cassandra - 검색하기 좋아요
- **컬럼형 DB**: ClickHouse, BigQuery - 집계 쿼리에 빨라요

저희는 결국 용도에 따라 섞어 썼습니다.

### 3. 카디널리티 관리
태그를 너무 많이 달았다가 메모리가 터질 뻔했어요.

```
✅ 이런 건 괜찮아요: service.name, http.method, http.status_code
❌ 이러면 망해요: user.id, request.timestamp, random.uuid
```

사용자 ID 같은 거 태그로 넣으면 진짜 큰일납니다.

## 📈 써보니 이렇게 좋더라고요

도입하고 몇 달 써보니 확실히 달라졌습니다:

- **장애 찾는 시간 진짜 줄어듦**: 예전엔 하루 종일 로그 파헤쳤는데 이젠 10분이면 원인 파악돼요
- **느린 구간 바로 보임**: "어? 이 쿼리가 왜 이렇게 느리지?" 하고 바로 발견할 수 있어요
- **서비스 의존성 파악**: 실제로 누가 누구를 얼마나 호출하는지 명확해졌어요
- **용량 계획 수립에 도움**: 진짜 데이터 보고 서버 스펙 정할 수 있어요

특히 새로 온 팀원들이 시스템 구조 이해하는 데 엄청 도움이 됐습니다.

## 🚀 이제 시작해보려는 분들께

처음 시작할 때 이렇게 접근해보시길 권합니다:

1. **자동 계측부터**: 기존 코드 안 건드리고 Java Agent나 라이브러리만 추가해서 시작해보세요
2. **중요한 서비스부터**: 가장 핵심적인 사용자 플로우 하나만 먼저 적용해보세요  
3. **천천히 확장**: 안정화 확인한 다음에 다른 서비스들로 넓혀가세요
4. **팀이 쓸 대시보드**: 예쁜 차트보다는 실제로 개발자들이 매일 볼 화면 만드세요

처음엔 설정하는 게 좀 귀찮을 수도 있지만, 한번 제대로 해두면 정말 편합니다.

## 마무리

마이크로서비스 환경에서 일하다 보면 "도대체 뭐가 문제야?"라는 질문을 수없이 하게 됩니다. OpenTelemetry는 이런 답답함을 해소해주는 정말 고마운 도구예요. 

물론 처음 설정할 때는 "이게 꼭 필요한가?" 싶을 수도 있어요. 하지만 한번 맛보면 이거 없이는 못 살게 됩니다. 저희 팀도 이제는 새 서비스 만들 때마다 OpenTelemetry 설정을 기본으로 포함시켜요.

여러분 팀의 마이크로서비스도 가끔 미스터리한 장애로 고생하고 있다면, 한번 도입해보시는 건 어떨까요? 분명 도움이 될 거예요.
